# Stats Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> In this repo the dispatches use the `implementer` and `task-reviewer` agents ([way of working](../../way-of-working.md)).

**Goal:** Per-person streak, done, missed and time trained, for this month and all time: in the add-on (REST, MCP, the
push channel), as HA sensors, and as a stats card on the workout tab.

**Architecture:** The add-on computes stats from the logs on each read and publishes a `stats` message when the result
changes, hooked onto the same "after a change" point that publishes `today`. The integration relays it like `session`,
with a probe for an older add-on, and makes four sensors per person. A new Lit card shows the numbers.

**Tech Stack:** Python 3.14, FastAPI, SQLAlchemy 2, Alembic, FastMCP (add-on); Home Assistant custom integration;
Lit + TypeScript, Vite, Vitest (cards).

**Spec:** [`docs/superpowers/specs/2026-10-24-stats-design.md`](../specs/2026-10-24-stats-design.md). Read it first;
its §3 rules are the requirements.

## Global Constraints

- Hard rules of `CLAUDE.md`, especially rule 5 (tests through public interfaces, frozen clock) and rule 6 (every UI text
  from a language file; English base, Danish too).
- `api_version` stays 1.
- Stats are computed, never stored. `added_at` is the only new column.
- Local dates use the add-on's timezone (D36), through `TrainingDays.local_date`.
- Person colours in people order: `#B18CFF`, `#3DD6C6`, then `var(--primary-color)`.
- Two PRs (D29): Part S `feat: stats` (`addon/`, `docs/`), Part E `feat: stats card and sensors` (`custom_components/`,
  `cards/`, `tests/`, `docs/`, `scripts/`). Merge S first.
- Decisions D47 and D48 go with Part S, D49 with Part E (spec §7).
- Commits: Conventional Commits with the co-author trailer from the dispatch, `git commit -F <file>`.

## Review Focus

1. A first workout done late or across midnight must show as done, not vanish (spec §3.1). Test in S2.
2. Two programs on one date, one done and one missed, gives streak 0 whatever the ids (spec §3.2). Test in S2, both id
   orders.
3. Upgrading a step 5 database keeps every number (spec §3.1, migration 0004). Test in S2.
4. A people change during a workout never stalls the session's ticks (spec §4). Test in S1: the HA check runs outside
   the lock (a slow fake HA while another locked request runs).
5. A stats integration against a step 5 add-on says why its sensors are unavailable (`addon_too_old`). Test in E1.

### Task S3: The `stats` message

**Model:** opus · **Review:** yes

**Files:**
- Modify: `training_days.py` (an after-change hook), `sessions.py` (`_send`), `stats.py`, `app.py`, `api/ws.py`
- Test: `addon/server/tests/test_stats_push.py`, plus the existing ws helpers and stream tests in
  `addon/server/tests/test_ws.py` (`_connect_expect`), `test_session_push.py` (`_connect`) and
  `test_session_plan_walk.py` (~227–230)

**Interfaces:**
- Consumes: `StatsService.compute()` (S2).
- Produces:
  - `StatsService(engine, training_days, sessions, publish)`, adding `publish`.
  - `StatsService.publish_if_changed()` publishes `{"type": "stats", "data": Stats}` when `compute()` differs from the
    last one it published. There is one memory, in the service.
  - `TrainingDays.on_change: Callable[[], None]`, a no-op by default. `_publish_today()` calls it on **every** call,
    outside its `if view != self._published` branch, because a people change leaves `today` alone but changes stats.
  - `Sessions._send` calls `training_days.publish_today()` when the messages hold `session_completed` or
    `session_ended`, not only `done`. So counted extra sessions, pause-limit ends and the first counted session reach the
    hook.
  - In `app.py`, `training_days.on_change = stats.publish_if_changed` is set **before** `sessions.recover()` and the
    startup `reconcile_now()`, so the memory starts filled.
  - A new month reaches the hook through the minute loop's `reconcile_now()`, with no extra code.
- The ws connect snapshot adds `stats` after `session`, through `services.stats.view()`. A queued `stats` in the drain
  replaces it, like `today` and `session`.

  - "Nothing comes" is tested by causing a known next message and asserting it is next, because `receive_json()` has no

  - The tests:
  - `test_stats_follows_session_on_connect`: the order is hello, today, session, stats.
  - `test_newer_queued_stats_replaces_the_snapshot`: follow the existing `today` replacement test.

  - `test_uncounted_end_publishes_no_stats`.
  - `test_minute_loop_pushes_stats_on_a_new_month_only` (a fast interval): across local midnight on 31 October one
